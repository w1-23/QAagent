## 1. 已确认的设计

1. 核心 QA60 与补充 citation60 都是正式实验，分开运行、分析和报告。
2. 不建立两套 Gold，也不要求专家写标准答案。
3. 全部 120 道题统一由两名领域评审认证题目有效性；评审可由相关专业研究生承担。
4. 补充 citation60 只检查最终引用是否明确命中冻结 target chunk。
5. 核心 QA60 的答案质量由两套冻结 LLM 判官评分，分歧由预冻结 LLM 仲裁者处理。
6. 不报告 semantic-support 或原文语义支持率。
7. 冻结题可以公开；原始运行、判官响应、受限全文、评分和结果不公开。
8. 实验环境使用 G01 当日最后更新且实际上线的生产版本；G01 必须保存真实 Git commit/tree、部署 SHA、`/health`、模型和索引快照，不得用历史 `b22c178c0343d22c0bbe2e4cddda94e296f59280` 代替当前实测。
9. API 密钥、账号和 Cookie 只从安全环境读取，不写入仓库、表单、日志或对话。
10. 既往服务器与本地实验数据已经删除；本轮不得补造旧数据，所有新运行和判定从头留存。

## 3. 人工不需要做的事

1. 不写 Gold Answer、Gold Claim、Evidence Bundle 或 Atomic Slot。
2. 不逐条人工评分核心 QA60 的 180 个回答。
3. 不做 citation60 的人工语义支持判断。
4. 不逐条人工核对工具路由；确定性工具轨迹规则优先。
5. 不手工抄写结果数字；全部从锁定原始记录和分析脚本生成。

## 4. 题目有效性的五项检查

每位评审对每题填写 `0/1`：

1. 题目清楚且没有歧义。
2. 来源范围与题干一致。
3. 答案应可答，或 N 题应正确拒答。
4. 来源/附件/chunk 可访问且可定位。
5. 题干无答案、chunk ID、文件名或长原文泄漏。

五项均为 1 且决定为 `ACCEPT` 才有效。两名评审不一致时，由第三名领域评审或 PI
在仲裁表中给出最终决定。评审姓名不进入公开仓库，公开副本只保留假名 ID。

## 5. 机器负责的事

1. 建立 120 题×2 人有效性包并检查完整性。
2. 校验题面、target chunk、哈希、运行计划泄漏和文件存在性。
3. 执行 B0/B1/B2，保存请求、SSE、工具轨迹、回答、引用、失败和产物 SHA。
4. 补充 citation60 自动计算 target chunk、document、allowed corpus、wrong corpus、
   no-citation；检索到但未引用不计命中。
5. 核心 QA60 调用 judge 1、judge 2；不一致时调用 judge 3，并保留全部原始响应。
6. 自动生成统计表、图和 `analysis_manifest.json`。
7. 校验公开包不含密钥、私有账号、受限全文、原始日志和真实评分。

## 6. 正式运行前人工门禁

只有同时满足以下条件才可进入 pilot：

1. `07_scoring/validity/question_validity_LOCKED.csv` 有 120 题且全部 `ACCEPT`。
2. `qa60_LOCKED.csv`、补充冻结题和 180 行运行计划已锁定。
3. `model_config.json` 与 `judge_config.json` 状态均为 `READY`。
4. B1/B2 适配器通过真实接口测试，不返回虚构结果。
5. 来源许可、账号隔离、模型版本和索引 generation 有证据。
6. 所有密钥仅存在于安全环境变量或凭据存储。

## 7. 修改与复现规则

任何题目、目标 chunk、有效性、判官、运行计划、终点或统计口径的修改，都必须：

1. 写入 `change_log.csv`；
2. 保存旧文件、旧 SHA 和修改理由；
3. 生成新版本目录或新锁定文件；
4. 不删除旧运行、失败或判官响应；
5. 在论文中报告协议偏离。
