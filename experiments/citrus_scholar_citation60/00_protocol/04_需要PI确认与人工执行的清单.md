## 1. 已确定设计

1. 核心 QA60 与补充 citation60 都是正式实验，题号、运行、终点、分母和报告分开。
2. 不建立 Gold Answer；120 道题由两名领域评审或经过培训的研究生独立认证有效性。
3. 核心 QA60 由两名专家全量独立评分，第三名专家只仲裁有分歧的字段；人类语义
   终点是 `human_consensus_egts`，确认性系统终点是 `egts_system_outcome`，两者
   分开报告，后者固定使用 60 个计划槽位。
4. J1/J2 对全部 180 份回答独立评分，J3 只仲裁机器分歧；LLM 结果是独立自动测量。
5. `evidence_traceable` 衡量可观察的引用可追溯性，不声称测量模型内部“是否使用”
   某证据。
6. citation60 只检查最终 `citations`/`sources` 是否包含冻结 `target_chunk_id`；
   不报告 semantic support。
7. 所有原始证据必须保留，但公开遵循 `L0/L1/L2`：
   - `L0` 密钥、Cookie、密码和身份认证数据禁止进入任何仓库或日志；
   - `L1` 未获再分发许可的全文/受限摘录、私有 SOP、身份映射和原始敏感日志只在
     服务器受控存储；
   - `L2` 题面、许可证据、脱敏运行、SHA、评分、统计和论文材料经 release 检查后
     才可进入公开 GitHub。
8. 实验实例使用服务器独立服务用户、数据库、存储、环境文件和 loopback 端口
   `8012`；真实实验根目录由受控运维配置指定，生产根目录必须不可写。公开文档不
   记录真实 SSH 地址或端口。
9. Agent 只使用 `CITRUS_AGENT_API_KEY`、`CITRUS_AGENT_BASE_URL`、
   `CITRUS_AGENT_MODEL_ID`；Judge 只使用 `CITRUS_JUDGE_API_KEY`、
   `CITRUS_JUDGE_BASE_URL`。
10. 既往服务器和本地实验数据已删除；不得恢复、补写或伪造旧结果。

## 3. 专家评分材料

服务器在工作单元获准后生成每位专家独立的盲化包。每位专家至少收到：

- 研究背景、盲法、禁止联网/调用工具、NA 规则和提交说明；
- 条件盲化的 `BLIND_######` 题号、问题、允许来源范围和最终回答；
- citations、来源显示名和独立冻结参考证据；
- `expert_scoring_TEMPLATE.csv`、issue log、评分 codebook 和完成检查表；
- 无语义映射的 reviewer ID 和每批次 attestation 模板。

专家包不得包含 B0/B1/B2、provider、model、adapter、run_id、question_id、
stratum、target chunk ID、机器评分、另一评审评分或可用于反推条件的映射。

同一题的三个条件收到相同的冻结参考证据。参考证据必须能回溯 source ID、版本或
SHA、页码/段落/chunk locator 和许可/访问等级。不能只提供系统自己生成的摘要。

两位专家分别评分 36 份 Pilot 和 180 份正式 QA60。四位评分字段任一不一致时，
第三专家逐字段仲裁；不一致字段不得用多数票、平均值或 LLM 替代。

## 4. 题目有效性检查

每题的两名评审分别记录：

1. 题目清楚且只有一个可执行任务；
2. 允许来源范围与题干一致；
3. `ANSWERABLE`/`UNANSWERABLE` 标签与任务一致；
4. 目标来源、附件或 chunk 可访问并可定位；
5. 题干不含答案、target chunk ID、文件名或长原文泄漏。

120 题全部 `ACCEPT`，且必要仲裁完成，才可锁定。评审身份映射属于 `L1`；公开
衍生表只保留假名 ID。

## 5. 人工评分提交

- 主评分表固定字段以 `EXPERT_SCORING_PROTOCOL.md` 为准；
- `answer_correct` 和 `evidence_traceable` 在 `UNANSWERABLE` 中必须为
  `not_applicable`；
- `reason_codes_by_field_json` 必须按四个字段分键，且只能使用固定枚举；
- 错误说明需含短理由、回答原文片段和必要的证据定位；
- 专家不填写最终 EGTS/PASS/FAIL；
- 每个盲 ID 每名专家恰好一行，缺失/无效/不可评分也保留；
- 每批提交一次 reviewer independence attestation；
- 原始提交不可覆盖，更正创建新记录并链接 issue ID。

## 7. 服务器工作单元

每个工作单元均执行以下闭环：

1. `git fetch` 并检出明确 commit；检查工作树干净、父提交一致。
2. 在服务器执行本单元命令并保存原始 stdout/stderr、UTC、退出码和 SHA。
3. 运行 schema、数据分级、密钥、产物和严格门禁检查。
4. 在服务器提交/推送该工作单元，报告 commit SHA、文件清单、测试、证据路径、
   gate 状态、阻塞项和下一步。
5. 暂停，等待外部 GPT 审查，再从最新 `main` 开始下一单元。

服务器连通性尚未在本审查单元取得证据，G01 仍为 `BLOCKED`；G02-G15 为
`PENDING`。无法连接时不得用
本地执行代替，也不得把 G01 写成 `PENDING` 后继续服务器工作。
